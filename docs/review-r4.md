## Verificado OK

**Kill-switch (WhatsApp, las 3 vías nombradas en el brief):**
- `dispatchSalesTurn` resuelve scope → `resolveAgentConfigStrict` → `row?.enabled === false` → return (`sales-agent.ts:391`). `db-error` → throw retryable → buffer re-encola. Turno deshabilitado = ingestado pero silencioso (semántica correcta).
- Queue drain `drainPendingInboundTurns` (`inbound-pipeline.ts:914-924`) usa el mismo `turnDispatcher` → misma barrera, más `hasRecentOperatorMessage` (`:917`) igual que la vía live (`:756`).
- Auto-reply chequea `enabled` (`inbound-pipeline.ts:476`) — kill-switch también corta saludos.

**Auto-reply / redirect ordering y claim semantics:**
- Operator gate (`hasRecentOperatorMessage`, `:756`) ANTES de auto-reply (`:765`) — humano gana, correcto.
- Claim-at-most-once por conversación vía `platformMessageId` único (`auto-reply:conv:<id>`); claim fallido/duplicado → skip; send fallido → claim row borrada para retry (`:528-537`). `webOrderRedirectEnabled` suprime el greeting (`:478`).
- `webOrderRedirectFor` config-gated: `enabled !== true` → null; url requerida o mensaje custom; prompt directive nunca inventa links (`sales-agent.ts:271-279`, `prompt-builder.ts:146-155`).

**Scoped credentials:**
- Fail-closed en ambigüedad: múltiples matches / múltiples activas sin routing key → `mismatch` (`channels/accounts.ts:294-300`, `messaging/accounts.ts:468-499`). Unknown `credentialsRef` (vault:, typos) → throw, no empty creds. Env `env:PREFIX` resuelve `PREFIX_API_KEY`/`ACCESS_TOKEN`/`WEBHOOK_SECRET` con vacío → throw.
- Secretos nunca cruzan al cliente: `listChannelAccounts` devuelve solo metadata; saves son write-only (vacío=keep, `CLEAR`=wipe, otro=encrypt). Webhook verify usa el `webhookSecret` de la cuenta resuelta (`ingress.ts:138`), `timingSafeEqual` + fail-closed en ambos lados (`webhookSecretMatches`).
- `db-error` → `ChannelAccountResolutionError(retryable)`/`AgentConfigResolutionError` — nunca degradado a global/placeholder; `schema-not-ready` solo con evidencia positiva (SQLSTATE 42P01/42703/3F000).

**Zernio embedded connect (requisito usuario):**
- `startZernioConnect`: admin-gated, zod strict, allowlist `whatsapp|instagram|facebook`, nonce 16B en cookie httpOnly/lax/secure-on-https/per-platform/10min; authUrl devuelto y el browser navega (`ChannelsView.connectZernio` → `window.location.href`). Cookie se borra si Zernio no devuelve authUrl (`channel-connect.ts:85-90`).
- Callback `/admin/canales/conectar/zernio`: `authorizeAgentApi` antes de todo → platform allowlist → `timingSafeEqual` con length-check + one-shot delete → upsert `channel_accounts` sobre el unique real `(provider, provider_account_id)` → redirect a `/admin/canales` con flash. Enrichment `fetchZernioAccount` best-effort no fatal.
- Manual API-key path intacto para los 3 providers (+telegram): form con `credentialsRef` validado por zod (`agent_config` o `prefix:VALUE`), `createChannelAccount`/`setChannelAccountStatus` admin-gated. `registerZernioWebhookAction` funciona y valida `ZERNIO_API_KEY`+`ZERNIO_WEBHOOK_SECRET` (`channel-connect.ts:94-102`). Embedded y manual conviven (mismo unique → upsert).

**Business API / hours:**
- `/api/business` expone solo campos no-secretos (name/address/phoneDisplay/whatsappPhone digits-only/instagram/website/description/hours formateadas); fallback env sin tirar; rate-limited `public:business` 20/200 propio. `/api/whatsapp-phone` igual, respuesta mínima.
- `formatBusinessHours` cubre ambos shapes persistidos (array admin + mapa inglés), colapsa rangos, `undefined` cuando no hay datos — horarios display-only sin tz, correcto para su uso.
- `/api/agent/test` (POST) + `/api/admin/test-agent` (GET): `authorizeAgentApi`, reporte con booleanos (`hasCredential`, `enabledTools` count), nunca valores secretos; ping read-only GET a endpoints del provider.

**Rate limit infra:**
- Sliding-window por key + bucket aislado por propósito; buckets por ruta (`inbound:<channel>`, `webhook:<provider>`, `public:*`, `cron:*`). Right-most XFF documentado (válido tras proxy de Render; spoofable sin proxy — tradeoff documentado, no bug).
- Inbound per-sender con key account-scoped (`inbound-pipeline.ts:602-624`): rate-limited → libera marker + 429 para redelivery limpio.

**Admin UI forms:**
- `AgentConfigForm` → `saveAgentConfig`: zod strict + `enabled: z.boolean()` requerido, scope key fail-loud (`parseScopeKey` null → error), tools filtradas al registry cerrado, read-then-write en el scope EXACTO (no hereda secretos de scopes más amplios), `copyAgentConfig` con field-pick explícito (id/scope/audit nunca copiados).
- `initial.enabled = config?.enabled !== false` → filas nuevas/ausentes defaultean ON en UI (no mata scopes accidentalmente).
- `BusinessSettingsForm` → `updateSetting` con allowlist de claves (ver HIGH-3 para el gate).

**Migration `0013_agent_enabled.sql`:**
- 11 columnas, todas `ADD COLUMN IF NOT EXISTS`, idempotente, no crea filas. Match exacto con `schema.ts`: `enabled bool NOT NULL DEFAULT true`, `auto_reply_24h`/`web_order_redirect_enabled` DEFAULT false, mensajes text nullable, 6 `*_enc` text nullable.
- Default `enabled=true` conserva comportamiento existente — el merge NO apaga configs. `agent_config_id_seq` creada en `0011` con `setval` correcto; `AGENT_CONFIG_ID=1` consistente.

**Asimetría benigna (nota, no finding):** `messaging/accounts.ts:315` pliega `botTokenEnc` de telegram en `apiKey` y `channels/accounts.ts:193-200` en `accessToken`; no rompe nada porque el send real de telegram usa `sendTelegramMessage(botToken)` directo desde la fila global — no `account.credentials`.
