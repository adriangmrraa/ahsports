## Verified OK

- **`POST /api/leads` input hardening** (`route.ts:39-79`): per-IP rate limit in an isolated `leads` bucket before any work; body measured twice (header fast-path + real bytes, 8 KB cap); zod `safeParse`; **phone re-validated after `normalizePhone`** (`/^\d{7,15}$/`) so digit-stripping can't smuggle `""` into the unique index; 23505 → clean 409 via `isUniqueViolation` (`helpers.ts:5-10`, matches code **and** wrapped message).
- **Signed-data trust boundary** (`route.ts:86-92`): verified ref attribution **overrides** client-sent `campaignId/adsetId/adId/platform` — forged signed codes keep the raw `refCode` but lose all carried ids. (See the unsigned-4-part gap above.)
- **`ref-code-sign.ts` crypto**: `timingSafeEqual` with length pre-check (`:34-35`); secret only from `SESSION_SECRET` env via `getSessionSecret()` which **throws when unset — no fallback** (`env.ts:109-115`); `resolveAttributionFromRef` is fail-open and can't throw into lead creation. Payload/`toString(36)` round-trips exactly between sign and verify.
- **`/api/admin/ref-code`**: `authorizeAgentApi()` → session cookie + `admin|gerencia` role (`rbac.ts:36-41`, verified `route.ts:19`); session cookie is `httpOnly`+`SameSite=lax` (`auth.ts:44-46`) so cross-site POSTs can't ride it; zod regex `[A-Za-z0-9-]` on all ids guarantees minted codes can't contain `_` and break the 5-part format.
- **`lead-capture.ts` first-attribution**: insert uses `onConflictDoNothing({target: leads.phone})` (race-safe) then an UPDATE that `coalesce`s only **empty** fields — `channelAccountId`, `contactId`, `refCode`, campaign ids, `name` are stamped once and never migrated; activity fields (`lastMessage*`, `updatedAt`) always refresh. Caller wraps it in try/catch (`inbound-pipeline.ts:742-751`) → never kills the webhook.
- **`conversions.ts` CAPI**: `server-only`; token from `META_CAPI_TOKEN` env only (never DB); PII sha256-hashed after proper normalization (digits/lowercase-trim); `not_configured` gate mirrors the YCloud pattern; 8s `AbortSignal` timeout; deterministic `event_id` (`lead_<uuid>`) is the correct dedup shape — and since the pixel never fires `Lead`, there is no double-counting today. Wired: invoked from `POST /api/leads` (`route.ts:139`).
- **Admin pages**: `/admin/leads`, `/admin/analytics`, `/admin/analytics/link-generator` all call `requireAgentAdmin()` (admin|gerencia) on top of the admin layout's `requireUser()` (`(admin)/layout.tsx:11`); sidebar links exist (`adminNavigation.ts:85-86`); `status` filter whitelisted against `statusLabel` keys; all search/filter values parameterized (no SQL injection path); single aggregate/joined queries — **no N+1** (`Promise.all` of 5 aggregates on analytics).
- **Analytics queries** (`queries.ts`): `campaign coalesce(utm_campaign, campaign_id)` correctly merges UTM and ref flows; the funnel's `orders.contactId IN (subquery)` is a single set-based query — correct semantics and no per-row blowup.
- **Migration `0014_leads.sql`**: column-for-column match with `schema.ts:1037-1073` including the **partial** unique index `leads_channel_external_uq WHERE external_user_id IS NOT NULL`; `lead_status` enum predates it (`0000_core_schema.sql:33`), `channel` enum exists (`0000:49`, values `telegram`,`whatsapp` — matches `ChannelKind` persistable set); FKs to `channel_accounts`/`contacts` with `ON DELETE SET NULL` match; registered in `_journal.json` idx 14 (all 19 migrations journaled).
- **Dropped GET /api/leads**: SocialCRM's session-gated GET was for its API-consumed leads page; AH's page queries the DB server-side — nothing missing.
- **`utm-capture.ts` helpers themselves** are correct (cookie encode/decode, URL param whitelist); the finding is the missing consumer, not the implementation.
- **`WhatsAppCta`** escapes its href correctly and hides when unconfigured — the gap is only the missing attribution payload (see UTM finding).
