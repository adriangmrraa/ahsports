## Verified OK

- **Pipeline order** (`handleInboundMessage`, `inbound-pipeline.ts:555-844`): delivery-marker claim → missing-identity ack → `platformMessageId` dedup → rate limit (429 releases marker) → media download (non-fatal fallback) → canonical `persistCustomerInbound` → contact link → media attachments → lead capture → operator gate → auto-reply → buffer enqueue + durable enqueue + scheduled flush + settle. Media runs pre-persist by design because the derived text IS the stored content; attachment rows are written post-persist once the conversation↔contact link exists.
- **Redelivery**: replayed deliveries exit at the marker (`:588`) or platform-id dedup (`:604`, intake duplicate `:705`) → lead capture, auto-reply, media downloads and enqueue are NOT re-run. Marker released on persistence failure (`:686`) and 429 (`:626`) so retries aren't permanently skipped.
- **Durable queue** (`inbound-queue.ts`): atomic skip-locked claim (single `UPDATE … SELECT … FOR UPDATE SKIP LOCKED`, :278-292); `runAfter` = debounce+30s grace lets the in-process flush win (:164); stale `running` reclaimed past the 10min lease (:88); `settleInboundTurnJob` is idempotent and self-gating (lock + `hasNewMessages` + `deadLettersBefore` delta, :210-237); backoff `10s·2ⁿ` capped 5min, `MAX_ATTEMPTS`=5 → `dead` (:347-376); partial live unique index matches migration 0012; `requeueDeadInboundJob` resets attempts/`runAfter`, dead-only, swallows 23505 when a live job exists (:544-569). Crash between enqueue and flush leaves a `queued`/`running` row the drain rebuilds from `chat_messages` — at-least-once holds.
- **Buffer** (`buffer.ts`): per-key lock, sliding debounce, bounded callback retries → dead-letter (:327-343), level-2 content dedup, post-release orphan re-check (:281). `scheduleBufferProcessing` resolves on success AND exhausted retries, so `.then(settle)` always runs.
- **DLQ surface**: `GET /api/admin/dlq` → `authorizeAgentApi` (401/403); `retryDlqJob` → `requireAgentAdmin` + Zod + dead-only requeue + drain kick; page → `requireAgentAdmin`. Un-migrated installs return empty via 42P01 handling.
- **Media** (`media/inbound.ts`, `downloader.ts`): per-provider `extraAllowedDomains` (global list never grows), size caps on declared+actual bytes, magic-byte validation + declared-mime match, per-ref failure isolation, non-fatal placeholder fallback, auth headers scoped per provider host. Attachment rows are written once per delivery transitively via upstream dedup.
- **Unified ingress** (`route.ts`, `ingress.ts`): signature verified before any event processing, per-account-secret matching (F7), fail-closed account resolution (non-ycloud), worst-status aggregation returns 503 on any retryable event, bounded body + per-IP limit + event cap. `import "@/lib/whatsapp/register"` present (B-01) on this route AND the dedicated `/api/whatsapp/webhook/[token]` route; `whatsappSalesDispatcher` routes non-whatsapp channels to the default dispatcher so telegram keeps `routeTelegramOperator`.
- **Passive persistence (D-01)**: `handlePassiveChannelEvent` claims the delivery marker before writes, dedups on `platformMessageId`, persists conversation+message for whatsapp/telegram/instagram/facebook (marker-only for sms/reddit), echoes → operator/agent rows by `echoOrigin`, releases the claim on persistence failure.
- **Auto-reply** (`auto-reply.ts` + `maybeSendAutoReply`): one claim per conversation via the `auto-reply:conv:<id>` platform-id unique insert; `alreadyReplied` + `conversationHasMessages` gate before claiming; failed send releases the claim row for retry; kill-switch (`enabled===false`) and `webOrderRedirectEnabled` take precedence; runs AFTER the operator gate so a human-active thread never gets the greeting.
- **Operator gate pairing**: `sendOperatorReply` (operator-send.ts:215) stamps `senderKind:"operator"` in the same partition the gate queries — genuine human replies do suppress the agent as designed. `deliverAgentReply` (sales-agent.ts:199-226) persists before send and suppresses the send on persist failure — the earlier suspected swallowed-persistence path does NOT exist. `stampDeliveryResult` handles the echo/23505 race.
- **Intake** (`channels/intake.ts`): transactional conversation upsert + message insert, account-partitioned conflict targets, duplicate → audited success, failure audit outside the transaction.
- **Echoes** (`handleEcho`): business-side sender must match an account before touching a conversation (foreign echoes dropped), own-bubble content suppression within 30s, deterministic synthetic pmid for id-less echoes.
- **Dedicated WhatsApp webhook**: path-token + Meta signature over raw body + zod envelope, delegates `handleNormalizedEvent` — signature contract unchanged.
- **Typecheck**: `tsc --noEmit` exit 0 at `4d01e5e`.
